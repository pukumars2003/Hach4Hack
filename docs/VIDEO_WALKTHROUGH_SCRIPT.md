# 5-Minute Judge Walkthrough

**Topic:** Hack4Hack team formation and concurrency
**Target duration:** About 4 minutes 45 seconds

## 0:00–0:40 — The problem

**Visual:** Open the team board and briefly show the project architecture in the README.

> "Hi, I'm Ajay. Hack4Hack helps participants find teams, manage join requests, and discover potential
> teammates. The central engineering challenge is correctness when many people try to join the same team
> at once: the final seat must go to one person, without overfilling the team."

## 0:40–1:50 — Race test

**Visual:** Open the **Race test** tab and select 50 racers.

> "Our join operation uses a guarded PostgreSQL update inside the membership transaction. PostgreSQL
> serializes changes to the team row, and a database uniqueness constraint also prevents a user from
> joining two teams in the same hackathon.
>
> The automated test sends 50 concurrent requests for one seat. The latest recorded run produced one
> successful join and 49 conflict responses, with the team still at 4 out of 4. The browser lab also offers
> larger runs up to 250 racers; that is a UI option, separate from the automated 50-request test."

**Action:** Run the 50-racer UI test and show its outcome. Do not narrate a specific response time; it varies
by machine and database.

## 1:50–2:45 — Participant experience and admin

**Visual:** Show the board, then sign in as a participant and open **My team**.

> "The board lets participants browse teams and filter the list. A participant can create a team, request to
> join, or join using an invitation. Team members can use the team workspace to coordinate requests and
> membership.
>
> Suggestions are explainable heuristic rankings based on skill fit, timezone, and interest signals; they
> are not generated by an AI model. Admins have a separate searchable, paginated user directory, so the
> entire seeded dataset does not have to be downloaded into one page."

For a demo login, use `user00001` or `user00001@demo.test` with `Demo@12345`. The public demo admin is
`adminbro` / `DemoAdmin#2026`; these credentials are for judging only.

## 2:45–3:25 — Live updates and data integrity

**Visual:** Open the app in two windows and show the board updating after a team change.

> "The API sends live updates to connected clients through Server-Sent Events. PostgreSQL notifications
> are tied to the transaction, so clients are notified after a committed change and then refetch the current
> data. Capacity and one-team-per-hackathon rules are enforced in the database, not just in the UI."

## 3:25–4:15 — Scale results and limitations

**Visual:** Open `docs/LOAD_TEST_REPORT.md`.

> "On a fresh local k6 run, the realistic 100-user mix measured 95.68 milliseconds p95, and the 250-user
> run measured 183.35 milliseconds. At 500 users it measured 272.41 milliseconds p95 with 1.60 percent
> errors, so that run did not meet the target. These figures are from the current local database; its row
> count was not separately audited. The k6 generator and API shared this Windows machine, and we did not
> record RAM or CPU usage, so local resource pressure is plausible but not confirmed. A dedicated-server
> run may differ; it still needs measurement. Older full-seed measurements use a different warm-up and data
> setup, so we keep them separate in the benchmark report."

> commands are `npm run db:migrate`, `npm run seed`, `npm run dev`, and `npm test`. The latest local
